# 什么是二值信号量？

有位同学在学完我的《从0手写嵌入式操作系统》课程中的信号量实现部分后，同时参考了FreeRTOS的实现源码，他发现：

> FreeRTOS里除了计数信号量，还有专门的二值信号量。

于是，这位同学提出疑问：二值信号量到底是什么？为什么需要单独搞一个二值信号量？

在这篇文章中，我将从问题出发，介绍为什么需要二值信号量、以及什么是二值信号量。

## 问题需求

假设在串口中断uart_isr中，每收满一帧数据，就释放信号量，通知处理任务parse_task解析数据帧。其代码如下：

```c
/* 中断里：每收满一帧就release一次 */
void uart_isr(void)
{
    if (frame_ready())
        rt_sem_release(rx_sem);  /* 连续收3帧，计数累加到3 */
}

/* 任务里：take一次处理一帧 */
void parse_task(void)
{
    while (1) {
        rt_sem_take(rx_sem, RT_WAITING_FOREVER);
        parse_frame();  /* 计数3→2→1，被唤醒3次 */
    }
}
```

一旦处理任务比较慢，有可能还没来得及处理第一帧，中断又连续收满了第二帧、第三帧。此时，uart_isr将连续释放两次信号量，使得信号量的计数最终变成3。此时，parse_task任务将连续执行三次数据解析函数parse_frame()。

> 如果程序中只为数据帧的接收设置了一个帧的缓冲区，这将导致只能存放这三帧数据中某一帧。
> 而parse_task任务以为有三帧要处理，最终实际上拿到的可能还是旧数据，只能丢弃或报错。

分析上述现象，可以找出问题的根源在于：**计数信号量会忠实地累计释放的次数，但在某些场景，我们只关心"有没有事件发生"，不需要累计"发生了几次"。** **这种多余的累计反而会导致任务被虚假唤醒。**

那么，有没有一种信号量，不会进行计数的多余累加？这就是二值信号量。

## 什么是二值信号量

二值信号量是一种特殊的信号量，它的计数值只能在**0和1**之间变化。

> 它的含义非常简单：
> 
> - 计数为0：当前没有待处理的事件，任务必须阻塞等待。
> - 计数为1：当前有一个待处理的事件，任务可以直接拿走并继续运行。

可以看到，与计数信号量最大的区别在于：二值信号量的计数最大只能是1，即使连续释放多次，计数也只会保持1。

这意味着二值信号量**记不住事件发生了多少次，它只表达"现在有没有一个待处理的事件"**。这恰恰是事件同步场景最需要的特性。

## 二值信号量的API示例

在FreeRTOS里，提供了面向二值信号量的API，主要接口有：

```c
/* 创建二值信号量，创建后初始值为0 */
SemaphoreHandle_t xSemaphoreCreateBinary(void);

/* 获取信号量，第二个参数是超时时间 */
BaseType_t xSemaphoreTake(SemaphoreHandle_t xSemaphore, TickType_t xTicksToWait);

/* 释放信号量（任务上下文使用） */
BaseType_t xSemaphoreGive(SemaphoreHandle_t xSemaphore);

/* 释放信号量（中断上下文必须用这个版本） */
BaseType_t xSemaphoreGiveFromISR(SemaphoreHandle_t xSemaphore,
                                   BaseType_t *pxHigherPriorityTaskWoken);
```

需要注意的是，并不是所有的RTOS都提供独立的二值信号量API。例如，RT-Thread仅提供了通用的信号量创建接口rt_sem_create()，没有单独的二值信号量API。

## 总结

综上所述，**二值信号量是一种计数值只能在0和1之间变化的特殊信号量，专门用于事件同步场景。** 

和普通计数信号量相比，二值信号量不会累计事件次数，不会导致任务被虚假唤醒，非常适合中断与任务之间、任务与任务之间的单次事件通知。
